Risk Mitigation
DCU hardware
Tamper or physical intrusion
An adversary with physical access can extract signing keys, inject malicious firmware, or silently corrupt the data stream — breaking every downstream security guarantee.
:
  • Enclosure shall be tamper-evident; any intrusion is detectable and logged
  • Secure element shall self-zeroize keys upon tamper detection
  • Firmware shall only execute code signed by the OEM certificate chain
  • Physical access requires two-person authorisation and a maintenance log entry
Digitisation
ARINC-717 bus loss is silent
If the data bus goes down, the DCU receives no input but may continue packaging empty frames — creating the appearance of a healthy stream with no actual flight data inside.
:
  • DCU shall continuously monitor sync word presence and frame counter progression
  • Bus loss shall be logged as BUS_FAULT with timestamp — not silently absorbed
  • Empty frames from bus loss shall be marked BUS_LOSS so investigators see the gap explicitly
Timestamping
GNSS spoofing — falsified timestamps
A spoofed GNSS signal injects a false UTC time into every chunk header. The chunks pass signature and hash checks perfectly. The flight timeline is corrupted with no visible anomaly.
:
  • GNSS time shall be cross-validated against ARINC-429 avionics time bus; divergence above threshold is a spoof indicator
  • Time jumps exceeding a defined rate-of-change limit shall be rejected and logged as TIME_ANOMALY
  • Authenticated GNSS (SBAS or Galileo OS-NMA) shall be required where available
Chunking
Session ID collision across flights
Two flights sharing a session ID are indistinguishable on the ground. Combined with a replay attack, an adversary can substitute one flight's data for another's in the archive.
:
  • Session ID shall be a cryptographically random 128-bit value — never a sequential counter
  • Entropy source shall be hardware-based (TRNG in the secure element)
  • Ground station shall maintain a session ID uniqueness register and alert on any collision
Merging
Out-of-order arrival causes scrambled reassembly
Wireless channel reordering causes chunks to arrive out of sequence. A naive ground station reassembling by arrival order produces a temporally scrambled data record — unusable for investigation.
:
  • Ground station shall reassemble exclusively by Chunk Index — never by arrival order
  • Any gap in Chunk Index sequence shall be flagged MISSING_CHUNK and trigger a retransmit request before session is finalised
  • Session shall only be marked COMPLETE after receiving and verifying the Session Close Chunk
Compression
Lossy compression applied silently
A configuration error or silent fallback could switch the algorithm to a lossy mode. FDR/CVR data is permanently degraded. This is unrecoverable — no post-hoc fix exists once the original is gone.
:
  • Only lossless algorithms are permitted; lossy modes shall not exist in DCU firmware
  • Compressed output shall be verified against input via a reversibility check before encryption; any lossy artefact causes a hard fault and falls back to uncompressed transmission
  • Compression algorithm selection is a permanent system configuration — not a runtime parameter
ECDSA signature
Signature scope excludes chunk metadata
If the ECDSA signature covers only the encrypted payload and not the metadata (session ID, chunk index, timestamp), an adversary can swap header fields between chunks without breaking the signature — silently reordering or mis-attributing data.
:
  • Signed input shall be: SHA-256(encrypted_payload ‖ session_id ‖ chunk_index ‖ seq_no ‖ timestamp ‖ source_flag ‖ payload_hash)
  • This canonical scope shall be a formally specified system requirement, independently verified at acceptance testing
  • Ground station shall reject any chunk where verified scope does not match the defined canonical form
Encryption
Nonce reuse — AEAD security collapses
For AES-GCM, reusing a nonce with the same session key is catastrophic: an attacker can recover plaintext and forge authentication tags. The encryption provides zero protection from that point forward.
:
  • Nonce shall be derived deterministically from Session ID + Chunk Index + Sequence Number — guaranteed unique per chunk per session
  • Nonce construction algorithm shall be formally verified — no runtime nonce generation that could repeat
  • Ground station shall verify nonce uniqueness during session reconstruction and alert on any collision
Encryption
Encryption failure → plaintext fallback
If an encryption error triggers a silent fallback to plaintext transmission, raw FDR/CVR data traverses the wireless channel unprotected — exposed to any receiver within range.
:
  • Encryption failure is a hard fault — DCU shall halt transmission and raise a maintenance alert immediately
  • Transmitting plaintext recorder data is explicitly prohibited in all operational modes — no exceptions
  • Only permitted fallback: buffer locally and resume encrypted transmission after fault recovery
Storage / buffer
Ring buffer in volatile memory — power loss destroys pre-trigger data
The 20-minute pre-trigger buffer is the entire value proposition for post-accident data recovery. If it lives in RAM, the one scenario where it matters most — sudden power loss — is exactly when it is destroyed.
:
  • Ring buffer shall reside in non-volatile, flight-ruggedised storage — not RAM
  • Write performance shall be validated against maximum ingest rate to prevent write stalls
  • On power restoration, DCU shall detect and recover any intact buffer segments before starting a new session
